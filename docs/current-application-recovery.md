# Current application recovery (MVP)

Refs #1055. This maintenance path supports original Glivela Entry, independent Senulun Agent and Komari Agent instances after a reviewed host replacement. It does not resurrect retired Meridian, change application IDs or grant new package permissions. Managed Senulun uses its existing managed recovery flow.

1. Review the replacement identity, settle outstanding work and approve the new network using the existing recovery UI. Preserve the original external node IDs, subscription identities and counters.
2. On each application owner, revoke/rotate the original node credential. For Glivela retain the original business node and configuration while replacing its certificate. For Senulun rotate the original node token, not an enrollment token. For Komari rotate the original client's token. Retain evidence privately; never upload credentials.
3. POST the reviewed `operationId`, `planRevision`, `applicationId` and complete `config` to `/api/v1/agents/{id}/reinstall-applications/current`. This authenticated administrator endpoint accepts only the original non-secret configuration, the saved package and saved permissions. Supply new secret fields for Glivela/Komari. For independent Senulun omit enrollment_token and supply `senulunRestore: {nodeId, token}` for the original node with its newly rotated token. Secrets use the existing encrypted execution channel and are not returned.
4. Wait for the exact deployment's authenticated result. An install result is **not** business acceptance. Unknown or failed attempts require outcome inspection; do not blindly repeat installation.
5. Verify the original identity on the application owner. Check fresh monitoring reports after token rotation. For Glivela parse the original subscription and perform actual authenticated HTTPS client traffic through the restored entry and its original routes. Check that non-target nodes, subscription identities and accounting are unchanged. Preserve a redacted evidence file outside the repository.
6. POST `operationId`, current `planRevision`, `applicationId`, `originalIdentity`, the evidence file's `evidenceSha256`, credential `rotationReference`, `businessReference`, and `verifiedAt` to `/api/v1/agents/{id}/reinstall-applications/current/verify`. References are short non-secret identifiers. Verification must follow this installation and be less than 15 minutes old.
7. Complete recovery with the existing endpoint/UI. Center revalidates the replacement, reviewed network, immutable install, authenticated result and current recorded verification in its final transaction before publishing application receipts and lifting the fence.

## Evidence boundary

Independent business verification is explicitly **operator-attested**, not an automated Center check. Center authenticates the administrator and replacement Agent, verifies the installation result and binds the external evidence reference/digest to that recovery operation. It does not independently authenticate the contents of an externally retained evidence file, inspect the independent service's database, or infer credential revocation from a changed value. The operator must actually perform steps 2 and 5 before recording them. An online Agent, open port, install receipt or arbitrary success flag is not sufficient acceptance. The UI labels this distinction.

This narrow maintenance interface does not add a plugin framework or automatically replay historical secrets. Other application families still fail closed. It is not an authorization to change another host.
