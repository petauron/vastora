# 数据库基线压缩（alpha MVP）

关联：petauron/vastora#1074。

## 范围

基线 123 的业务结构与 122 相同。删除 4–122 历史迁移文件及专属升级用例，
不保留旧版本兼容分支。新安装直接创建完整当前结构，仅记录 0 和 123。
现有 122 库原地压缩迁移记录，不新建库、不导出导入业务数据。
版本号不回到 1，避免旧程序误识别，后续迁移从 124 开始。

## 现有库转换

1. 运维先确认运行版本、数据库 `PRAGMA user_version` 为 122，迁移记录最大版本为 122 且全部已应用。
2. 保留完整 Center 数据目录备份，尤其 `center.key` 与数据库必须配对；不把凭据或完整配置写到公开日志。
3. 在维护窗口停止旧 Center，再由新版本独占打开原数据目录，不能让两个版本同时写入。
4. 程序先核对外键和 SQLite 完整性，然后通过 `VACUUM INTO` 保存一致的 122 快照到私有 `migration-backups/`，文件权限 0600。
5. 单个事务仅替换 `goose_db_version` 记录并将 `user_version` 推进到 123。账号、节点、部署、订阅、流量、密文、业务触发器和关联全部原样保留。
6. 再次核对完整性及外键。重新打开时不重复压缩、不重复备份。

更早的数据库不在新程序中重放旧迁移。先在备份副本上使用压缩前的已发布
schema-122 版本升级，完成它要求的历史任务处理，再进入本流程。
不得仅手工修改版本号来绕过检查；不能把任意旧库标成 122。

## 失败与恢复

备份或检查失败则停止启动；事务提交前失败会回滚迁移元数据。
提交后的检查失败仍拒绝启动，保留原快照供恢复，不自动降级数据库。
恢复必须先停止 Center，配对恢复快照与原 `center.key`，用对应旧版本打开；
不要在运行中覆盖数据库，也不要把旧 WAL/SHM 与恢复快照混用。

## 验证状态

现有 fresh/migrated 等价用例改为覆盖 122→123，比较所有业务表内容、
备份内容、迁移记录压缩及重复打开；保留错误版本拒绝检查和业务功能用例。
本轮未运行本地测试、CI 或生产转换。完成代码不代表已完成数据转换验收。
